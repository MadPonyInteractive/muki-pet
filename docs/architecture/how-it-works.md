# How the mod works

## Files (`muki-pet/` in this repo)

| File | Job |
| --- | --- |
| `.claude-plugin/plugin.json` | Manifest: name `muki-pet`, version, MIT licence. |
| `hooks/hooks.json` | Names the hooks module: `{ "modules": ["./register.tsx"] }`. |
| `hooks/register.tsx` | Wiring only: each Claude Code event goes to the brain (`send`), `ui.render` on `AbovePrompt` goes to `band/render.tsx`. |
| `hooks/brain/machine.ts` | **The core loop.** Pure `step(state, event, now)` → next state + effects (start/cancel timer, redraw, save home). Runs the activity table, then each behaviour in `BEHAVIOURS`, then shows the mood with the highest priority. |
| `hooks/brain/activity.ts` | **What he is doing:** named states `idle`, `working`, `asking`, `sleepy`, `asleep` and `ACTIVITY_TABLE` (state × event → state). `asking` remembers what he was and the ids of the tools waiting for your OK (`asked`), and goes back when the last of them ends (`toolDone` with its id) or the turn ends. Mood votes: asking/curious 30, the rest 10. |
| `hooks/brain/behaviours/` | **What he does on top**, one file each, all extending the abstract `Behaviour<S>` in `behaviour.ts` (one level deep; no `$`): `reaction.ts` (passing moods alert/happy/sad, priority 20), `celebrate.ts` (the passing mood `celebrate`, priority 25), `attention.ts` (lonely/mad/tantrum, priority 15), `visit.ts` (prop visits; moves home), `papers.ts` (the paper pile's count and his visits to it), `remote.ts` (the Remote Control headset), `hold.ts` (the one redraw-hold rule: wait while you hover + 3 s grace, or while a visit runs; must be last). The list is `BEHAVIOURS` in `machine.ts`. Each keeps its own slice in `State.slices` and namespaced timers (`reaction.flash`, `celebrate.end`, `attention.next`, `remote.idle`, `remote.settle`, `hold.visitEnd`, `hold.nearEnd`, `activity.sleepy`, `activity.asleep`). |
| `hooks/brain/types.ts` | State, Event, Effect, Request (`Effect` or `{ type: 'emit', event }` for in-place internal events `visitStarted`, `released`), MoodVote, DrawingOptions. |

The last context figure is saved per chat. |

| `hooks/brain/pile-store.ts` | The paper pile per chat in `$.store`, so a reload of the mod keeps it (the brain itself is reset by a reload). |
| `hooks/character/` | **What he is, as data: one definition per thing.** `moods.ts` (each mood: lasting or passing, how long, stays home, face rules), `props.ts` (each prop: which tools drop it, its shape), `heat.ts` (each level: from which %, colours, lid droop, sweat; `heatOf`), `palette.ts` (colours, sizes), `tuning.ts` (timings: sleep, prop gap, near grace, fade-in, visit lead-in, easings), `geometry.ts` (band height, edge, `bandX`, `visitPlan`), `papers.ts` (the pile: most papers drawn, visit gaps, `pilePlan`), `confirm.ts` (`isConfirmation`: is a message a short "it worked"). | `hooks/band/render.tsx` | The band: asks the runtime for heat and home, picks the drawing, double buffer, JSX. |
| `hooks/band/sensor.ts` | A `Client` surface module: tells the hooks when your mouse is over the band (see Moods § No redraw while you're with him). |
| `hooks/band/frames.ts`, `drawing.ts` | Double buffer (two slots, 0.9 s swap); drawing cache per width/mood/heat/home. |

| `hooks/draw/compose.ts` | Puts the body parts together and loops over `FEATURES`: root classes, CSS, defs and each feature's markup in its slot. |
| `hooks/draw/feature.ts`, `features/` | **Pluggable drawing features**, one file each, all the `Feature` shape `{ name, rootClass?, css?, drawingCss?, defs?, slots? }`: `touch`, `sleep`, `tantrum`, `mad`, `heat` (CSS generated from `character/heat.ts`), `headset`, `celebrate`, `visit`, `papers`, `cookies/` (`cues`, `cookie`, `eating`, `game`, `sick`). | `hooks/draw/moods.ts`, `wander.ts`, `keyframes.ts`, `math.ts` | Faces as CSS, the simulated route, keyframe writing, small maths. |

Machine tests include one per behaviour and one for the activity table. |
| `tsconfig.json` | Type-check config: extends the engine-written `.claude-plugin/types/` (see Dev workflow). |

**Loader rules found during the refactor:** a hook passed to `on()` must be a top-level function declaration (or imported one), and `$` may only be passed to functions declared at the top of the mod's own files: no methods, no factories or callbacks that take `$`. So the runtime and the double buffer are plain functions over module state.

## How the drawing works

The robot is **one self-animating SVG**, drawn with `Svg` and `isInteractive` (Desktop puts it in a script-less sandboxed frame where CSS animation and `:hover` work).

1. `draw/wander.ts` simulates about 45 to 60 s of motion at 30 fps **around a home spot** (`simulate(W, homeX, seed)`, cached per width and home in `routeAround`): rest at home, a short trip out, a look around, back home, repeated; the loop starts and ends resting at home. Also the head spring and the eye direction. Home is a share of the band (`home`, 0 to 1, `x = 44 + home * (W - 88)`), so a resize keeps him at the same share.
2. Each track is thinned to the samples that linear interpolation can't stand in for, then written out as CSS `@keyframes` (cached per width, home and pace in `keyframes.ts` `routeAround`). The widest drawings are about 100K characters (the heaviest, a tantrum at heat 3 with a pile of 6 and the headset, is in the size test in `register.test.tsx`); the limit is 131,072. Most of it is the click strips, which grow with the width.
3. Mouse reactions are pure CSS: about 50 to 100 narrow invisible strips ride along with the robot (`.c0`, `.c1`, ...: 24 px wide near him, 40 px from 300 px out, 64 px from 800 px out), and `:hover` on a strip turns the eyes by its gaze class (`.gK:hover ~ .bot .gz`, 6 levels). Hovering the band pauses the motion (`animation-play-state: paused`). `!important` overrides the paused eye animation without knocking it out of sync with the body.
4. **Coin game** (the cookie game's base, below): the same strips have `tabindex="0"`, so a click focuses one. Each strip's own rule sets `--d` (its distance from him), `--w` (wheel turn), `--t` (dash time) and `--s` (side) on itself and its later siblings. `.c:focus ~ .bot` transitions him to `translateX(var(--d))`; `.mv:focus-within` pauses his loop so he dashes from a frozen spot. Each strip is followed by its own coin (`.c:focus + .cu`, a `<use href="#cn">`), so every click pops a fresh coin. The roll back is an animation (`home`, from `translateX(var(--d))` to none over `--r`, starting at `--t` + 1.9 s, `forwards`), with `spin` for the wheels and `leanb`/`swingb` for the head. The strip's focus ends by itself after it: `.c:focus{animation:gone 0s calc(var(--t) + var(--r) + 2.2s) forwards}` hides it and the frame drops focus. He is already at rest by then, so nothing moves (checked: no transition starts). An early blur (clicking on him mid-run) still rolls him back over 1 s by `.bot`'s own transition.
5. Touch: four invisible strips over the robot (`.p0`…`.p3`) sit in `.bot` before the body (`.bd`, which ignores the pointer). `.bot:active` is the press, and `.bot:active>.pN:hover~.bd .pt` leans the head while you drag. The release wiggle uses `.bot:not(:active) .wg{animation:...}`: the rule starts matching again on release, so the animation restarts.
6. The hooks module sends the same string every time for the same options, so redraws don't restart the animation.
7. **Heat** is a class on the svg root (`h0` to `h3`) with static rules (`.h2 .sw1{display:inline}` etc.). The mood is also a class there (`m-happy`); tests read the mood from it.
8. **Props (visits):** `tool.call` (main loop, before `next(e)`) maps the tool to a prop and starts a visit in `brain/behaviours/visit.ts` (at most one per 12 s, not while asleep). `visitPlan(width, fromHome, n)` (pure) decides where the prop goes, where he stops beside it (`toU`, his new home) and the timeline. The visit drawing's route is the one around the new home, held with `.s{animation-delay:<visit length - elapsed>s; animation-fill-mode:backwards}` (so he rests at the new home until the visit ends), and `.ix` starts offset back at the old home and rolls him over. While a visit runs, `band/drawing.ts` keeps the visit drawing (only a width change rebuilds it) and `brain/behaviours/hold.ts` holds mood and heat changes until it ends (+0.3 s), restarting a waiting passing mood's timer so it gets its full time; each moving part runs one whole-visit keyframe track (`vx` on the new `.ix` wrapper around strips, coins and `.bot`; `vw` on a new `.vw` wrapper in each wheel; `vl` head; `vg` eyes; `vd` lids; `vq1`/`vq2` the "?" and "!"; `vpa` the prop), delayed by `-elapsed`, so a drawing made mid-visit (a mood change) picks it up where it is. In a visit drawing only the shifted route keyframes are sent (not the cached ones too), which keeps visit drawings under the size limit.

Why this way, and not a frame-by-frame redraw: see `research/mods-api.md`.

## Moods

- The brain (`brain/`) decides what he feels: the activity state gives a lasting mood (neutral, focused, sleepy, asleep, or curious while asking), `behaviours/reaction.ts` a passing one (alert, happy, sad, on the `reaction.flash` timer), and the highest priority wins. When the result changes the runtime calls `$.ui.invalidate('ui.render')`, unless `behaviours/hold.ts` holds the redraw.
- Each mood (or heat level, or width) is its own SVG source, so a change means a new frame, blank until it loads. Three tricks hide that:
  - **Double buffer:** the band has two slots, each a column Box. The new drawing goes into the free slot, in the flow; the old slot turns `position="absolute"` (top/left/right 0) and stays on top for 900 ms (`$.clock.after`), then is emptied. A second change while a swap is running replaces only the frame loading underneath (or, if it goes back to the drawing on top, that one simply takes over), so the frame on top is never thrown away mid-swap. A frame stays in the same slot for its whole life, so Desktop's morph finds the identical iframe in the same place whether it matches by position or by `isEqualNode`. The alt is constant (`'Muki, a small robot on two wheels'`), because the alt is part of what the morph compares.
  - **No double buffer on a width change:** a new width replaces the drawing outright (one slot, no old one on top). Opening a chat always renders at 784 px, then 792 px, and Desktop has just rebuilt the band from the chat's last drawing, so that "old" frame restarts too, at its own spot, and keeping it on top showed two robots. See `research/mods-api.md` § Opening a chat.
  - **A visit drawing never outlives its visit:** a visit always schedules a redraw (`hold.visitEnd`) at the visit's end + 0.3 s, and `band/drawing.ts` rebuilds a cached visit drawing once no visit is running, so the band's last drawing is a plain one at the new home. (A chat opened again replays its last drawing from the start; a visit there rolled a second robot to the new home.) A mood that waited during the visit (`deferred`) gets its full time then; one that didn't is left alone.
  - **Visit lead-in 1.5 s** (`LEAD` in `character/tuning.ts`): he starts toward the prop only after the 0.9 s swap plus a margin for a late redraw while the app is busy.
  - **Continuity:** every drawing starts him resting at his home spot; the hook only keeps `home`. Why: each frame starts its own clock when it loads, which can be long after the hook thinks (a frame made while the window isn't showing may load only when it shows again), and hovering pauses him without the hook knowing, so the hook can't know where a running drawing has him. With a home spot, two drawings disagree only if he was out on a trip at the swap, by at most that trip.
  - **No redraw while you're with him:** a redraw while he's away from home (cookie game, a trip, paused by your mouse) jumps him home. So while your mouse is over the band nothing redraws and no prop drops: the keyed band Box is a hover scope, and its hover squeezes an absolute 0-tall Box to 0 wide; the `Client` in it (`band/sensor.ts`) sees the resize and posts `{ over }` to the `ui.message` hook in `register.tsx`, which sends the brain a `near` event. The brain defers every redraw (`brain/behaviours/hold.ts`), and `band/drawing.ts` hands back the shown drawing on any render. On leave it waits `NEAR_GRACE_MS` (3 s, `character/tuning.ts`) for a cookie still being eaten, then draws what waited. The new robot in a swap stays hidden 0.75 s (`FADE_IN`), so the two overlap for 0.15 s, which hides the new frame's load (hiding him for the whole 0.9 s makes him blink out on every redraw).
  - **Smooth face change:** in the new frame `.bot` is hidden for 0.15 s and fades in over 0.25 s, and each face part that differs gets `animation: fN .45s ease-out .15s backwards` with `@keyframes fN{from{transform:<old face>}}`, delayed so it doesn't play while the new frame is still hidden under the old one (`@starting-style` would). The alert and happy hops wait 0.2 s for the same reason.
- `robotSvg(width, options)`: the route keyframes are cached per width, home and pace; the rest (root classes, mood CSS, features) is built per call. A width or heat change passes `from = mood`, so the face doesn't slide.
- Every mood hook calls `next(e)` and returns its result untouched, with the mood code in `try`, so it can never block or change a tool call or turn.
- **Attention:** `behaviours/attention.ts` keeps `since` (the last play: a `near` on/off pair at least `PLAY_MS` apart, or the first event seen) and votes `lonely`/`mad`/`tantrum` at priority 15 (over the activity's 10, under passing moods' 20). One timer, `attention.next`, is restarted only when the next step's time changes. The steps depend on heat: `TIRED_HEAT` (2, i.e. 30%) and over has only `lonely` after `TIRED_LONELY`. Asleep it votes nothing. Its redraws go through the hold like any mood change. He falls asleep `ASLEEP_AFTER` (15 min) after the last reply, and asleep he shows no need, while mad and tantrum come `MAD_AFTER`/`TANTRUM_AFTER` (15/20 min) after the last play: in a quiet chat he is asleep before the tantrum (and usually before mad), so those show in a busy chat, and a waiting question (curious, 30) hides all three (by design, Fabio's call). To test the ladder, lower the three `*_AFTER` values in `character/tuning.ts` for a while (2/3/4 min worked).
- **No redraw from play (rule):** your reaction-worthy play (pet, boop, cookie) happens while he may be out on a wander trip, and every new drawing starts him at his home spot, so a redraw caused by play jumps him (up to a trip's length) right under your eyes. His reaction to play therefore lives in the drawing's CSS, never in a brain mood or anything else that redraws. Guarded by the test "play with him while he wanders never redraws him" in `brain/machine.test.ts`. (Only `lonely`/`mad`/`tantrum` ending on play still redraw: that is the point of them.) A `pleased` mood on play was tried and made him jump (log 2026-11-22).
- **Plain eyes after play:** touching him (hover over him for more than .3 s, a pet, a boop) or a cookie puts his mood's eyes aside (plain open eyes). They stay plain for `GLOW` (15 s, `character/tuning.ts`) after you go, then his mood's eyes (sleepy, sad, curious, lonely, ...) slide back; a mood that doesn't change the eyes shows nothing extra. It is a delayed transition back: the base `.eye`, `.top`, `.pt` rules in `parts/face.ts` carry `transition: transform .45s GLOW`, while the hover rules (`touch.ts`, with a .3 s delay so a mouse just crossing him doesn't count), the pet lean and the cookie focus (`cookies/game.ts`) carry their own undelayed transitions. Mood changes slide by animation, so the delay doesn't touch them, and a transition never plays on load. Only the eyes, no mouth or cheeks (Fabio's choice).
- **Celebrate:** at `turn.start` (main loop) `character/confirm.ts` `isConfirmation(e.text)` matches a short "it worked" (bare "1", "works", "perfect", "looks good", ... up to 40 chars, no "?"); the `turnStart` event carries `confirmed`, and `brain/behaviours/celebrate.ts` votes the passing mood `celebrate` at priority 25 (over passing moods' 20 and the work's 10, under a waiting question's 30) on its own `celebrate.end` timer, restarted on `released` like reaction.ts. `draw/features/celebrate.ts` draws five firework bursts in the `behind` slot and the `party`/`cheer` keyframes, only in that mood's drawings, so no other drawing changed.
- **Headset:** `register.tsx` sends `prompt` with `prompt.submit`'s `origin.kind`; `brain/behaviours/remote.ts` (slice `{ on, changing }`) puts it on for `bridge` (your phone or the web) with a `remote.idle` timer (`REMOTE_IDLE_MS`), and takes it off for a desk origin or when that timer fires. While `changing` (`HEADSET_SETTLE_MS`, timer `remote.settle`) drawings play the drop or the lift; after it they show it at rest, and that settle is a change too, so the band's last drawing is never the drop or the lift (a reopened chat replays its last drawing). Its changes reach the band through the hold like any mood change, so a phone message while your mouse is on him is drawn once you go.
- **Slow when tired:** `compose.ts` passes `slow = TIRED_SLOW` to `routeAround` at heat 2+, which stretches every roll in `wander.ts` (same random sequence, so the cool drawings are unchanged).

## Cookie game: counting clicks in a row with no script

- The click strips (narrow focusable `rect`s that travel with him, each setting `--d --w --t --r --s` for the robot by `.cN:focus~*`) now come in **six layers** (`L1`..`L6`, the same strip set repeated, `y`/`height` set in CSS to save space). Only `L1` takes clicks normally; `svg:has(.Lk:focus) .Lk+1{pointer-events:all}` makes the next layer clickable while a strip of the layer below has focus, so each click during a sequence climbs one layer. A focus ends by itself (the `gone` animation hides the strip), which resets the count.
- **Restarting animations on the always-shown robot:** an animation only restarts when its name changes, so odd layers use one set of keyframes (`homeA`, `leanA`, ...) and even layers another (`...B`); `L6` uses set `C` plus the sick animations. `eatingCss()` in `draw/features/cookies/eating.ts` builds a set.
- **Cookies:** one per layer, placed after the robot (drawn in front of him), hidden until its layer has focus; going from `display:none` to shown restarts its own animations, so the cookie rules are shared. Bites are a `<mask>` per cookie with three circles that grow (the mask must come after the strips in the document for the `~` rules to reach it). The bites all come from the bottom edge, left to right, each overlapping the last, so the cookie stays round (spread around the edge they leave a three-pointed star).
- **A click on him mid-game feeds nothing (Fabio's pick):** the focused strip shrinks to his size (`x:-26px;width:52px`) and rides with him: the same dash transition and a `ride` roll-home animation as `.bot`. The layers are written top-down (`L6` first, `L1` last), so the focused strip lies over the next layer's strips, and a click on him hits the strip that already has focus: no focus change, no cookie, no snap. Which strips take clicks uses `:has()`: while any strip has focus, only it and the next layer do. It shows `cursor:grab` like him. Once he is home (`stay + --r`) it steps aside (`aside` keyframes: `pointer-events:none`) and his touch strips come back (`tchA`/`tchB`, alternating by layer so each cookie restarts the timer), while the focus still waits `LET_GO` for the next cookie, so he takes clicks again as soon as he's home. **Petting him while he's out:** a press on him lands on the riding strip, so `.c:focus:active:not(.L6)~.bot .hrt` floats the hearts up (and the cursor shows `grabbing`) without touching the focus; the game goes on. Not while he's sick. The touch strips still step aside in a game (`.c:focus~.bot .p{pointer-events:none}`): a boop would move the focus, drop the roll home mid-way and Chromium would snap him home (no transition starts from an animated value). Outside a game a click on him is still a boop. Proven with real clicks in the browser pane: at rest a boop; at the cookie and mid-roll home a click on him keeps focus and cookie 1; a click elsewhere drops cookie 2.
- **The 6th:** its focused strip grows to cover the whole band (`x`/`width` in CSS) so further clicks hit it and change nothing, and the robot ignores the pointer while he's sick.
- Lab proof: `tools/frame-lab-ladder-test.svg` (ladder, alternating names, mask bites, the growing 6th strip). Checked with `:focus` swapped for a class; the real click-to-focus was already proven by the coin game.

## Boops in a row and mad

- The four touch strips come in five layers (`q1`..`q5`, `features/touch.ts`), the same trick as the cookie ladder: a layer takes clicks only while `.bot:has(>.q(k-1):focus)`, and a focused strip hides (dropping its focus) after `IN_A_ROW` (1.5 s). So each click within 1.5 s climbs a layer. `q5` is wider (4 x 35 px) and its focus lasts 15 s: that is mad. While a `q5` has focus all of `q5` takes the mouse, so hovering its outer strips says which side the hand is on.
- `features/mad.ts`: the angry face for `.mv .bot>.q5:focus~.bd` and for `.m-asleep.h0/.h1 .mv .bot:hover` (woken), with `.mv` in front so it beats touch's happy-face rules; the dodge is a `.bd` transform with a springy transition.
- Tired (`.h2`/`.h3`): `q2` never takes clicks (`!important`) and the focus hands back after 0.8 s.
- The cookie game's "touch strips come back" animation (`tchA`/`tchB`) goes on `q1` only; on all `.p` it would make the wide `q5` clickable after a cookie.
- `features/tantrum.ts`: the steam and "!!" marks (shown by the tantrum mood) and the `stomp`/`shake`/`puff`/`bang` keyframes, 120 s cycles with the burst in the first 4 s, generated in code.
- Lab proof (hidden pane, `:focus`/`:hover` swapped for classes, transitions off): five hit-test-and-focus clicks on him climb `q1`..`q5`; `q5`'s hide is 15 s; angry lids under hover; dodge +30 px from the left strips, -30 px from the right; asleep hover = angry, no hop, no z's; at heat 2 the clicks stay on `q1` with 0.8 s. `tools/frame-lab-boop-test.svg` is the drawing used.

## Band width

The band reports its width in text cells (`bodyColumns`). The SVG width is `bodyColumns × 8 px`; he rolls the full band width in Desktop, so 8 px per cell is right (Fabio, 2026-11-22).

## Dev workflow

- **Preview without the app:** `node tools/preview.mjs <out-folder>` writes `robot.svg` and `index.html`. Serve that folder (`python -m http.server 8765 --bind 127.0.0.1 --directory <out-folder>`) and open `http://127.0.0.1:8765/robot.svg` in the browser pane. Opening `file:///` gives a static snapshot.
- **Checks** (all four before claiming done):
  - `npm run check`: TypeScript 7 type-check of the mod (`tsc -p muki-pet`), from the repo root after `npm install` once. The root `package.json` holds dev tools only; the mod itself has no dependencies.
  - `node tools/golden.mjs`: hashes `robotSvg` and `visitPlan` over about 3,650 option sets (widths, moods, from-moods, heat, homes, visits, the paper pile and its visits, the headset) and compares with `tools/golden.json`. "identical" means no drawing changed. When a change is meant to alter drawings, run it with `--write` and say so in the commit.
  - `claude plugin test ./muki-pet` and `claude plugin validate ./muki-pet`, with the app's own claude.exe.
- **Where the types come from:** `muki-pet/tsconfig.json` extends `muki-pet/.claude-plugin/types/tsconfig.json`, which the engine writes (git-ignored, about 1 MB) beside a mod it hot-reloads from a dev-mods or `--plugin-dir` folder. It does not write them for a folder loaded through `CLAUDE_CODE_PLUGIN_DIRS`. The copy in the repo came from the old dev-mods copy, written by Claude Code 2.1.321 (first line of `claude-code/index.d.ts`). After a Claude Code update, refresh them by starting a session with `claude --plugin-dir ./muki-pet` once (per the plugin-authoring skill; not tried yet), or by copying a newer engine-written `types/` folder in.
- **Classes:** the loader accepts class syntax in the mod's files (spike 2026-11-22: abstract base, `extends`, `super`, `static`, `#private`, getter, all ran under `claude plugin test`). No class may hold `$` or take it in a method.
- **Getting it to load in a chat:** `muki-pet/` in this repo loads in every chat through `CLAUDE_CODE_PLUGIN_DIRS` in `~/.claude/settings.json` (next to `~/.claude/mods/context-bar`). Edit it here directly. An old copy under `~/.claude/dev-mods/<session-id>/` (where the plugin-authoring skill first put it) loads only in its own session and is obsolete: don't edit it.
- **After editing `muki-pet/`, type `/reload-plugins` in the chat** to see the change without starting a new one.
