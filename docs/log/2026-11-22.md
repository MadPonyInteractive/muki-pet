## Second chat: moods seen live, why they flicker, coin game groundwork

- **Fabio, live after `/reload-plugins`:** on mood changes he "teleports and flickers", mostly at the start of a chat ("quite a lot"), not during a long working turn (when the mood stays focused).
- **Fabio, hover and petting:** when he's in a mood and you hover or pet him, the eyes look wrong (the mood's lids stay on under the happy hover face), and he keeps that mood while the pointer is on the band instead of going back to neutral.
- **Cause found in the Desktop app's own code** (`ion-dist.asar`): the band is updated by a DOM morph that keeps an iframe only if it is byte-identical (source, alt, width, height). Each mood change is a new source, so a new frame: blank while it loads (flicker), then he restarts at the hook's guess of his loop time, which is wrong by every second he spent paused under the mouse (teleport). Details: `research/mods-api.md` § How Desktop really draws an interactive Svg.
- **Tried, to pass the mood in without a new frame:**
  - Frame size as a signal (CSS inside picks the face from its own width): works in Chromium, but needs an exact-px container, and the engine refuses a raw `div` ("not an element"). Box sizes are only `ch`/`lh`/`%`, which the frame can't decode. Dead end.
  - Freezing him with `!important` + a long transition instead of pausing (so the hook's clock stays right): Chromium never transitions from an animation's value, he snaps. Dead end.
- **Proved for the coin game** in `tools/frame-lab.html` (a copy of Desktop's exact frame setup: sanitizer, CSP, sandbox): a click focuses an SVG `rect tabindex="0"`, `:focus` sibling rules move a body and show a coin, and an animation to `visibility:hidden` ends the focus by itself after N seconds. So the whole coin sequence can be pure CSS in the frame.

(2) Above 30% context he gets warm: a little red, sweaty, a bit tired, more as it climbs. Context is readable like context-bar does it (`$.session.usage().context.percent`, the `session.measure` event).

## MPI-17 Phase 1: three bugs found by reading the code

- From the codebase review (none seen live). Each reproduced in a test first, which failed on the old code and passes on the new.
- **Band render safety net.** `band/render.tsx` ran everything after `next(e)` outside a `try`, so a throw in Muki's own code lost what other mods drew in the band (the context bar). Reproduced: a direct `renderBand` call whose `ui.resolve` throws rejected with "boom". Now the whole drawing is inside a `try` that returns `below`. A helper function for the body lost TypeScript's surface narrowing (`Svg` missing on the terminal's table), so the body stays inline. Also found: `runtime.ts` `loadHome` sent its first `homeSeen` outside its `try`, so one failed read would have stayed failed for every render of the chat (`homeLoad` is shared); moved inside.
- **Heat per chat.** `readHeat` saved the context figure under one store key for all chats, and a chat with no figure yet read it back: a new chat could start hot from another chat. Reproduced with a fake store and two session ids (chat B drew hot). New `brain/chat-store.ts` (`readForChat`, `saveForChat`: `{ <session id>: value }`, newest 20 kept) now serves the heat and the paper pile (`pile-store.ts`). An old plain-number value under `context` is ignored.
- **Curious ends on the asked tool only.** Any tool's end (a sub-agent's, a parallel one) ended "asking". Reproduced as a machine test. `toolAsk` and `toolDone` now carry `tool_use_id`; `asking` keeps the ids still waiting (`activity.asked`) and goes back only when the last ends; a turn's end still ends it; events with no id behave as before. My pick, per the plan: a sub-agent's failed tool no longer saddens him (`failed` needs `!e.agentId`), but its id still answers a question about it.
- Checks: tsc 0; plugin test 52/52 (3 new); golden identical (3,534); validate passes (usual warnings). Not seen live.
